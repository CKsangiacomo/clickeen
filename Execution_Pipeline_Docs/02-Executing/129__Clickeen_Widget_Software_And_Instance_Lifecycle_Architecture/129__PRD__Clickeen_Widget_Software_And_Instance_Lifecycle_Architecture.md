# PRD 129 — Clickeen Widget Software And Instance Lifecycle

Status: **CLOUD-DEV DEPLOYED — OWNER QA PENDING**

Owner: Clickeen product owner/architect

Date: 2026-08-17

## 1. What This PRD Fixes

Clickeen already has Widget software, editable account instances, Bob, Roma,
Tokyo-worker, Publish, and public serving.

Before this local PRD 129 implementation, the repository mixed four different
product actions into one client-rendering and materialization workflow. PRD
129 separates them:

```text
1. Create an editable instance of a Widget
2. Edit that instance and Save its editable source
3. Publish the saved instance when the user chooses and the account permits it
4. Serve the files generated by Publish
```

The largest correction inside Edit is preview. Bob must preview the current
browser-memory draft from the Widget software used for editing. It must not
load, parse, rewrite, or execute an instance's stored serving package. A
never-published instance has no serving package and must still open and preview
normally.

This is an architecture correction to the existing product. It is not a new
product, an FAQ-only architecture, or a compatibility project.

## 2. Product Truth

### 2.1 Widget software

A Widget is complete product software that performs one specific job.

Every Widget contains:

- the complete shared-and-Core document composition it uses;
- mandatory Core HTML, CSS, and JavaScript;
- its default state and Bob editing declarations;
- its customer-content declarations;
- its bindings to shared Clickeen capabilities and account policy;
- its internal Discovery declaration; and
- its Widget-owned product copy.

The Widget owns its product meaning. It uses Bob, Roma, Tokyo-worker, Dieter,
localization, policy, and every other Clickeen capability through the same
system contracts used by every applicable Widget.

### 2.2 Editable instance

An instance is one account's customized use of one Widget.

Its editable source contains the exact saved values for shared Stage, Pod,
Header, typography, appearance, and applicable shared features together with
the Widget's exact Core values and base-locale customer content.

The editable instance is not Widget source code and is not public browser
code.

### 2.3 Saved source

Create writes the first saved source for a new instance. Save later updates
that source while the user edits the instance in Bob.

The existing source files remain:

```text
instance.config.json
instance.content.json
```

They are two physical files for one logical editable instance:

- `instance.content.json` owns the exact declared base-locale customer-content
  paths and values;
- `instance.config.json` owns every other saved instance value and the
  instance metadata;
- the same value is never owned by both files.

Save is persistence inside Edit. It is not Publish and it does not generate
public browser files.

### 2.4 Published package

Publish is a separate user action.

Only an allowed Publish asks Roma's materializer to generate the browser files
for the exact saved instance:

```text
index.html
styles.css
runtime.js
```

All three files are mandatory. Together they are one published package.

### 2.5 Public serving

Tokyo-worker serves the stored published package. A public request never
creates, edits, saves, publishes, or rebuilds an instance.

## 3. The Four SubPRDs

| SubPRD | Product action | Starts with | Ends with |
| --- | --- | --- | --- |
| 129A | Widget Software And Create | Widget software plus New, Duplicate, or Template starting truth | One new unpublished editable instance opened in Bob |
| 129B | Edit And Save | Widget software plus one editable instance opened in Bob | Live source-only draft preview plus updated saved source; Bob remains available for more editing |
| 129C | Publish | Exact saved source plus explicit Publish intent | One stored published package, or one exact denial with no publication change |
| 129D | Serve | Public request plus stored publication truth | Browser receives the stored HTML, CSS, and JavaScript |

The handoff is deliberately simple:

```text
Widget software
  -> Create editable instance
  -> Edit and Save editable source
  -> Publish saved source
  -> Serve stored published files
```

No SubPRD may perform another SubPRD's job.

## 4. Create

Create has three starting modes:

- **New** starts from the Widget's defaults plus the account's shared Widget
  defaults.
- **Duplicate** starts from another exact saved instance, creates a new
  unpublished instance, and opens the duplicate in Bob.
- **Template** starts from a selected normal saved instance owned by the
  CLICKEEN admin account. The normal listed/admin-selected instances are the
  Template catalog; there is no separate template model, table, source shape,
  or storage root. The cross-account Duplicate that creates the new customer
  instance is follow-on implementation through the existing instance
  authorities.

All three modes end the same way:

```text
new unpublished editable instance -> Bob
```

Create writes editable source and unpublished publication truth. It does not
generate `index.html`, `styles.css`, or `runtime.js`.

## 5. Edit And Save

Bob owns one complete browser-memory draft.

The user can edit, preview, undo, use Product Copilot, and Save repeatedly.
Workspace preview combines the deploy-built Widget software with that draft in
Bob's isolated editing surface. It does not consume Tokyo-worker's stored
`index.html`, `styles.css`, or `runtime.js`, and public `runtime.js` contains no
Bob editing protocol.

Save persists the current editable source through Roma. It does not invoke the
materializer, replace public files, change publication state, or generate
localization output.

If a published instance is edited and saved, the currently published package
remains public until the user explicitly publishes again.

## 6. Publish

Publish happens only when the user clicks Publish.

An allowed Publish:

1. reads the exact saved source;
2. invokes Roma's materializer once;
3. generates complete `index.html`, `styles.css`, and `runtime.js`;
4. asks Tokyo-worker to store the generated files and publication truth; and
5. makes that stored package the public truth for the instance.

Publication truth commits before Tokyo's default Worker entrypoint purges its
own Workers Cache. If the commit
succeeds and the purge then fails, the command is not reported as full success
and the committed publication is not hidden as a failed Publish. Tokyo returns
the explicit purge error with the exact
`committed: { instanceId, status, changed }` transition. Roma reconciles the
visible state, shows a status-specific account-shell banner, and the existing
Republish or Unpublish command retries delivery refresh.

Every cacheable response carries the same deterministic
`accountInstanceCacheTag` for that exact account/instance. After an owning
mutation, the default entrypoint calls
`ctx.cache.purge({ tags: [accountInstanceCacheTag] })`, which invalidates the
instance's base HTML, support files, locale variants, and tracking-query
variants in the cache that actually owns them. The account publication Durable
Object returns committed truth to the default entrypoint and never purges from
its separate entrypoint scope.

A Publish denied by Roma's fast local capacity precheck performs no
materialization. A request that reaches Tokyo-worker but loses the final
account-atomic transition may already have materialized transient package
strings in Roma memory, but it persists no package or publication state and
does not change saved source or the currently served package.

Publish never silently Saves a dirty Bob draft. The user Saves first, then
Publishes the saved source.

## 7. Serve

Tokyo-worker serves the already-stored package for a published instance.

Serving does not call Bob, Roma, the materializer, a model, or Widget source.
It does not rebuild HTML, CSS, or JavaScript.

For a selected locale, Tokyo-worker expresses every present stable-coordinate
value from the exact stored locale overlay in the returned semantic HTML
before client JavaScript. Reorder follows saved identity; a newly added
identity remains intentional untranslated saved source content until Generate
Translations; and a deleted identity has no current node. Editable attributes
use the exact authored `data-ck-content-attribute` target. Tokyo-worker does
not create a second locale package, read old positional keys through a
compatibility path, or migrate overlays on a visitor request.

## 8. Free Model And Tiers

Widget access and public capacity are different products.

A Free user can:

- use every available Widget type;
- create multiple editable instances;
- duplicate, edit, preview, and Save them; and
- publish and serve one instance at a time.

The system capability `instances.published.max` owns public capacity. Free is
`1`; the system policy matrix owns every tier value.

The current matrix deliberately keeps Tier 1 at one published instance because
Tier 1 expands product features rather than public-instance capacity. Tier 2,
at five published instances, is intentionally the first multi-publish tier.

The prior `widgets.instances.max` Create-time gate conflicted with this model.
The local implementation removes that capability and gate rather than renaming
or repurposing it.

Widget-bound editing limits are separate. They apply once when the user tries
the governed edit. They are not repeated at Save or Publish.

### 8.1 Account Lifecycle

An account tier/status transition is account policy, not a fifth Widget
lifecycle action. It does not change what a Widget or editable instance is.
Every editable instance and its exact saved source remain intact; lower policy
applies at the next governed user action.

The settled suspended-account lifecycle provides day 0-30 public-serving
grace, automatic free-tier serving materialization at day 30 when recovery has
not occurred, and automatic account-root deletion at day 90 if the account is
still unrecovered. The account operation owns the exact allowed published set
and any tier-dependent package result. Public Serve does not inspect tier or
choose what stays live.

The scheduled lifecycle runner and complete account-root deletion operation
remain documented Account Management implementation gaps. They are follow-on
account work, not a PRD 129 Publish/Serve blocker.

## 9. Discovery And Enable SEO/GEO

Every Widget contains an internal `discovery.json` declaration. It tells the
system:

- what the Widget is;
- the Widget's Clickeen-owned baseline Discovery defaults;
- which exact customer-content parts matter to search and answer systems; and
- how those content parts relate.

The user does not edit `discovery.json`, and Bob does not generate an SEO
editor from it.

The existing shared account capability controls **Enable SEO/GEO**:

- every tier receives the Widget's Clickeen baseline title and description;
- Tier 2 and above may additionally enable optimization from their exact saved
  content.

The system owns tier truth and the shared control. The Widget owns its
Discovery declaration and baseline defaults. Roma's materializer uses both
only during Publish.
Only the materializer writes the technical discovery output included in the
published package. Serve only returns that stored result.

## 10. Authorities

| Authority | Responsibility |
| --- | --- |
| Widget software | Widget meaning, defaults, declarations, Discovery, Core HTML/CSS/JavaScript, and Widget-owned copy |
| Bob | Browser-memory editing, source-only isolated preview, undo, Product Copilot changes, and Save/Publish intents |
| Roma | Current-account Create, Save, Publish, policy, and Bob-opening commands |
| Roma materializer | Sole generator of instance-specific `index.html`, `styles.css`, and `runtime.js`, during allowed Publish only |
| Tokyo-worker | Physical account-instance storage, publication truth, and public serving of stored files |
| Dieter | Shared design tokens and UI primitives |
| Other Clickeen capabilities | One shared implementation used the same way by every applicable Widget |

No service may acquire Widget-specific meaning. No second editor, materializer,
storage root, or serving path is authorized.

## 11. Local All-Widget Implementation State

The local implementation now applies the four separate actions to Big Bang,
Cards, Countdown, FAQ, and Logo Showcase:

- New and Duplicate write unpublished editable source only;
- Duplicate opens the new instance in Bob;
- Bob opens and previews from the compiled Widget software plus its current draft,
  without reading a stored public package;
- one generic Bob edit decision applies Widget-bound limits before draft mutation,
  and one Roma Popup composes the exact denial;
- Save updates editable source only;
- explicit allowed Publish alone invokes Roma's generic materializer and stores
  complete `index.html`, `styles.css`, and mandatory `runtime.js` through
  Tokyo-worker;
- Roma's fast publication-capacity precheck is finalized by Tokyo-worker's
  account-atomic count/package/serve-state transition: a live overlap receives
  `409 PUBLISH_IN_PROGRESS`, while a later over-capacity request receives
  `402 UPGRADE_REQUIRED`, and the loser persists nothing; and
- Tokyo-worker serves the stored package and applies an exact requested locale
  overlay by stable identity to declared HTML content or authored attribute
  slots at the Edge before JavaScript.

All five current Widgets now use the canonical `widget.html`, `core/`,
`discovery.json`, `limits.json`, `labels/en.json`, and `upsell/en.json` source
topology. The retired flat CSS/client/label paths are absent. The generator has
one universal source contract and no compatibility discriminator or Widget
branch.

No suspended-account lifecycle runner or complete account-root deletion
operation was added. Their settled grace/materialization/deletion law and
current implementation gap remain with Account Management rather than
blocking the Widget lifecycle.

## 12. Existing Coordinates

Widget software remains under:

```text
tokyo/product/widgets/{widgetType}/
```

Account instances remain under:

```text
accounts/{accountPublicId}/instances/{instanceId}/
  instance.config.json
  instance.content.json
  serve-state.json
  index.html
  styles.css
  runtime.js
  overlays/
    locales/
      {locale}.json
```

The three browser files do not exist for a never-published instance. Their
exact replacement and publication-write mechanics belong to 129C.

## 15. Preservation

The all-Widget implementation preserves each Widget's existing product
behavior, saved values, customer content, ToolDrawer meaning, localization
coordinates, and shared
Stage, Pod, Header, typography, appearance, branding, social-share,
locale-switcher, asset, and account capabilities unless an exact change is
approved in the relevant SubPRD.

Architecture correction is not permission to redesign Widget functionality.

2. all five current Widgets follow the same Widget contract;

9. account publication capacity is enforced at Publish;

    deployed runtime truth; and

cross-account Duplicate is separate follow-on implementation and introduces no
template model. The account lifecycle runner/full deletion, deploy, cloud-dev
