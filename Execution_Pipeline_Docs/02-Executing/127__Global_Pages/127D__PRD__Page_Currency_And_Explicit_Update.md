# 127D — Page Update State

Status: **APPROVED FOR EXECUTION — EXECUTE AFTER 127A–127C ARE DEPLOYED AND VERIFIED**

Parent: `127__PRD__Global_Pages_Program.md`

Depends on: deployed and verified 127A–127C

## 1. Goal

Tell the customer when a saved Page must be updated because one of its saved
Widget Instances or that Instance's locale values changed, and provide one
explicit **Update page** action.

The implementation is one boolean: `needsUpdate`.

127D does not compare revisions, record dependency evidence, keep generated
history, run a Queue, or update Pages automatically.

## 2. Customer behavior

A saved ordinary Page has one of two states:

- **Current** — `needsUpdate` is false. Edit and Publish can proceed.
- **Needs update** — `needsUpdate` is true. Update page is available. A fresh
  attempt to enter normal Page editing and any Publish attempt are blocked
  until Update succeeds.

When the customer opens a Page that needs updating, Roma shows:

> One or more widgets in this page have changed. Update the page before editing
> or publishing it.

The modal provides **Update page** and **Back to pages**. There is no Needs
fixing state, revision history, or automatic repair. 127E implements and
verifies the Your pages status, modal, buttons, browser generation call, and
complete customer journey.

Templates do not have Current/Needs update status. They are reusable saved
source and are changed only through explicit template Save.

## 3. Authorities

| Responsibility | Authority |
| --- | --- |
| Saved Instance changes | Existing Roma/Tokyo Instance Save authority |
| Saved Instance locale-overlay changes | Existing Generate translations / Instance overlay authority |
| `needsUpdate` value | Tokyo Page `serve-state.json` |
| Update command and policy | Authenticated Roma Page route |
| New Page files | 127B Web Code Generator called by 127E Page Builder |
| Page storage and public purge | 127C Roma/Tokyo operations |

No new service or storage authority is introduced.

## 4. When the flag changes

Set `needsUpdate: true` after either of these existing writes succeeds:

1. every Save of an existing ordinary Instance when a saved ordinary Page in
   the same account references that Instance ID;
2. every locale-overlay write for an existing ordinary Instance when a saved
   ordinary Page in the same account references that Instance ID, including
   Generate translations and an approved exact localized-value edit.

For an Instance Save or Instance overlay write, the existing account operation
reads the account's saved Page sources and marks only Pages whose placements
contain that Instance ID. This is a direct same-account source scan, not a
dependency graph, index, Queue, job, or background compiler.

These are explicit successful writes. Roma does not compare bytes, timestamps,
hashes, revisions, or generated output to decide whether a write was a real
change. Setting an already-true boolean to true is harmless.

Page-owned source or locale-overlay writes do not set `needsUpdate`. They are
Page edits, and the customer's next explicit Save applies them through the
normal 127B/127C flow. **Save applies Page-owned edits; Update page refreshes
the Page from its latest saved Widget Instances.**

Set `needsUpdate: false` only after first Page Save or explicit Update page
successfully stores the new Page files. Publish, Unpublish, list, open, account
Settings changes, and public requests never change the flag.

If setting the flag after a named Instance Save or Instance overlay write
fails, the owning operation returns the normal error and the customer can retry
the same action. It must not report success while leaving the Page status
wrong. There is no special partial-success workflow, persisted failure state,
or recovery system.

## 5. Explicit Update page

The complete customer action delivered by 127E is:

```text
customer clicks Update page
→ from Your pages or a fresh open, Page Builder loads the saved Page
→ from an already-open Page Builder, it retains the current browser Page draft
→ Page Builder loads the latest referenced saved Instances
→ Web Code Generator creates the current Page files in the browser
→ Page Builder shows the generated result
→ Roma applies normal account, role, tier, entitlement, and Page checks
→ Tokyo stores the source/current files through 127C
→ Tokyo clears needsUpdate
→ Roma opens the Page as Current
```

127D extends 127C's authenticated Roma Save/Update boundary used by that flow.
It applies the flag gate and clears `needsUpdate` only after 127C accepts and
stores the Page source and current files already generated by 127B. 127D
verifies that extension with controlled submitted Page files. 127E owns the
Page Builder load, browser Web Code Generator call, modal, and end-to-end click
journey.

When a Widget is edited in slide-in Bob, Page Builder remains mounted. A Bob
Save sets the stored flag for a saved referencing Page and refreshes that
placement in the retained browser draft. The resulting **Update page** uses
that retained Page draft plus the latest saved Instances. Opening or closing
Bob never changes the flag. An unsaved Page has no stored flag and uses the
latest saved Instance on its first Save.

If Bob Save changes the flag while Page Builder is already open, the retained
Page draft is not discarded or disabled. **Update page** becomes the required
next persistence action; ordinary Page Save and Publish remain blocked until
that Update succeeds.

Update does not invoke Translation Agent. It uses whatever Page and Instance
overlays are already saved. Generation failure happens in 127E before the
Update request. Page-file storage follows 127C. Any rejected or failed Update
returns the normal error, and `needsUpdate` is not cleared unless the Update is
accepted successfully. No rollback, recovery record, candidate package,
transaction, or failure lifecycle is created.

## 6. Edit and Publish gate

- First Page Save has no existing flag to gate and initializes
  `needsUpdate: false`.
- Later ordinary Page Save and Publish mutation routes require
  `needsUpdate: false`; the explicit Update route remains available when it is
  true.
- In 127E, opening a Current Page opens Page Builder normally.
- In 127E, opening a Needs update Page shows the update modal before Page
  Builder.
- A Page already published remains publicly available from its last explicit
  successful Save/Update until the customer updates or unpublishes it.

`needsUpdate: false` only clears the Page-currency block. Existing account,
role, tier, entitlement, and Page policy must still authorize Edit or Publish.
Viewers receive no mutation action; tier-blocked actions use the existing
Upgrade interaction. This gate is ordinary Roma API policy over the stored
boolean, with the customer UI implemented in 127E. Tokyo public serving reads
publication state and the current files; it does not derive freshness on a
public request.

## 7. Pre-GA state cutover

127D does not add a compatibility reader or silently treat a missing
`needsUpdate` value as false. This pre-GA execution replaces the obsolete Page
implementation. New Pages initialize the field through first Save; obsolete
development Page data can be recreated through the normal Page Save operation
when needed. There is no migration framework or retained old state shape.

## 9. Verification

Prove:

- a referenced Instance Save marks only Pages that reference it;
- an unrelated Instance Save changes no Page flag;
- a referenced Instance overlay write marks only Pages that reference it;
- a Page-owned source or locale-overlay write does not set the flag and is
  applied by the customer's explicit Save;
- Settings changes, list/open, Publish/Unpublish, and public requests never set
  or clear the flag;
- first Save initializes false without silently defaulting a stored missing
  field;
- Needs update blocks later ordinary Page Save and Publish mutations while
  preserving explicit Update;
- the 127D extension of 127C's Update boundary accepts the current
  127B-generated Page files without adding another storage/policy boundary;
- successful accepted Update stores the Page files through 127C and clears the
  flag;
- failed Update retains the flag and reports failure;
- the last published Page remains available until an explicit successful
  operation changes it;
- missing `needsUpdate` is not silently read as false;
- no revision/fingerprint/evidence/graph/Queue/background/recovery path is
  introduced.

127E later verifies the Your pages status, accepted copy, modal, buttons,
browser generation, slide-in Bob Save/close behavior, retained Page draft, and
end-to-end customer journey. Run focused Instance Save, Instance/Page overlay,
