## 1. Goal

Create one shared browser-compatible Web Code Generator that writes complete
HTML, CSS, and JavaScript for Widget Instances and Pages.

The customer edits in Bob or Page Builder. Web Code Generator updates the
browser working files. Save submits those exact files through Roma, and Tokyo
stores them.

127B also removes the current visitor-side primary-content construction path.
Every saved Instance and Page must contain its meaningful customer content in
`index.html` before JavaScript runs.

## 2. What Web Code Generator is

Web Code Generator is deterministic browser-compatible repository code that
writes the public files for Widget Instances and Pages.

Its owner is:

```text
packages/ck-web-code-generator
```

Bob and Page Builder import it and run it in the browser.

It is not:

- a Worker or deployed service;
- an API or network hop;
- an agent or model call;
- a Queue, job, graph, registry service, or runtime lookup;
- a public-request dependency;
- another editor or server renderer.

The Bob Editor Compiler and Web Code Generator have different jobs:

- **Bob Editor Compiler** builds ToolDrawer controls from Widget editing
  contracts.
- **Web Code Generator** writes final public HTML, CSS, and JavaScript.

## 3. Source and file law

### Widget definition

Every Widget definition owns:

- its existing structured config/spec/editing contracts;
- complete default `index.html`;
- complete default `styles.css`;
- behavior-only default `runtime.js`;
- approved assets and product truth.

The default `index.html` contains the Widget's meaningful headings, copy,
items, links, images, and semantic structure. It is not an empty shell waiting
for JavaScript.

`index.html` is the Widget's only Widget-specific HTML source. Web Code
Generator uses one generic deterministic renderer to apply structured values,
conditions, and repeaters. It does not create a TypeScript HTML writer or
render switch for each Widget.

### Saved Widget Instance

Every saved Instance owns:

- `instance.config.json`;
- `instance.content.json`;
- existing exact locale overlays;
- customized `index.html`;
- customized `styles.css`;
- customized `runtime.js`.

Structured source remains what Bob, controls, and agents edit. The three files
remain what browsers receive. Neither replaces the other.

Saved Instance `index.html` is a complete standalone HTML document. When that
Instance is placed in a Page, Web Code Generator takes its generated Widget
root/body content for the declarative Shadow DOM placement; it never nests the
Instance's `<html>`, `<head>`, or `<body>` document inside Page HTML.

There is no `savedRevision`, build record, file fingerprint, package pointer,
or generated-from evidence.

### Saved Page

Every saved ordinary Page owns:

- `source.json`;
- `serve-state.json`;
- Page-owned locale overlays;
- generated `overlays.json`;
- generated `index.html`;
- generated `styles.css`;
- generated `runtime.js`.

A Page template owns the complete reusable Page source/config and the three
generated browser files. Its copied config retains Page values, placements,
settings, and direct asset references; only locale, overlay/translation, and
public-serving values are absent. It has no locale overlays, generated
`overlays.json`, or public publication state.

For both Instances and Pages, `runtime.js` contains behavior only. It does not
contain customer source or build the primary HTML.

## 4. Browser workflow

### Create and Duplicate

No new creation machinery is required.

```text
Create
→ open the selected Widget or blank Page as an unsaved browser draft

Duplicate
→ open a browser copy of the selected Instance or Page

Edit
→ update the browser working source and files

Save
→ create the saved Instance or Page through the existing Roma/Tokyo Save path
```

Nothing is written to Tokyo before Save. Leaving the draft uses the existing
unsaved-changes interaction.

127B does not define a new draft service, draft database, draft route family,
or temporary product identity.

This is a direct cutover of the current persisted-before-edit flow:

- `roma/components/widgets-domain.tsx` must stop POSTing Create to
  `/api/account/instances` before Bob opens;
- its Duplicate action must stop POSTing to
  `/api/account/instances/{instanceId}/duplicate` before the copy is edited;
- the matching Create/Duplicate routes, tests, and immediate Tokyo writes are
  removed or changed to accept only the later explicit Save;
- Bob must accept the unsaved definition/copy as browser working state and use
  the ordinary Instance Save operation to mint and persist the new Instance.

Execution must follow the existing Bob route and state conventions while
making this cutover; it must not invent a remote draft route or service.

### Preview and Save

Bob and Page Builder use different preview timing because they edit different
products:

- **Bob:** controls update one browser-memory Instance working copy containing
  structured source plus `index.html`, `styles.css`, and `runtime.js`. Web Code
  Generator updates those files during editing, and Bob previews them.
- **Page Builder:** draft controls update the editor's Page source and Workspace
  composition from the referenced saved Instance files. Draft control changes
  do not produce final Page files. Web Code Generator produces the final Page
  files only when the customer clicks Save or Update.

In both cases, the files produced for the explicit Save operation are the exact
files submitted through Roma. Roma applies its existing account, role, tier,
entitlement, and Save rules. It does not run Web Code Generator again or
produce different files.

## 5. Package API

The package exports two operations:

```ts
type WebCodeFiles = {
  indexHtml: string;
  stylesCss: string;
  runtimeJs: string;
};

type ResolvedWebCodeContext = {
  assetsByRef: Record<string, ResolvedAccountAsset>;
  typography: ResolvedAccountTypography;
};

type GenerateInstanceInput = {
  definition: WidgetDefinition;
  source: SavedInstanceStructuredSource;
  overlays: ExactLocaleOverlays | null;
  settings: {
    seoGeoAeoEnabled: boolean;
    includeClickeenAttribution: boolean;
  };
  context: ResolvedWebCodeContext;
};

type PagePlacementInput = {
  placementId: string;
  instanceId: string;
  source: SavedInstanceStructuredSource;
  files: WebCodeFiles;
  overlays: ExactLocaleOverlays | null;
};

type GeneratePageInput = {
  source:
    | Omit<AccountPage, 'pageId'>
    | Omit<AccountPageTemplate, 'pageId'>;
  settingsLocales: string[];
  pageOverlays: Record<string, PageLocaleOverlay>;
  placements: PagePlacementInput[];
  context: ResolvedWebCodeContext;
};

type GeneratePageOutput = {
  files: WebCodeFiles;
  overlaysJson?: PageServingOverlays;
};

generateInstance(input: GenerateInstanceInput): WebCodeFiles;
generatePage(input: GeneratePageInput): GeneratePageOutput;
```

These types describe the required product inputs. Execution may reuse existing
contract names and casing, but must not add another generation entrypoint.

Page generation does not require a persisted `pageId`. On first Save, Page
Builder adds the current account `baseLocale` to the ordinary ID-less browser
draft and passes that generation source to Web Code Generator. Roma still owns
minting `pageId` and reading the same current account `baseLocale` for the saved
Page source. Generated Page HTML therefore contains no temporary Page identity
or Page-id placeholder.

Bob and Page Builder resolve account assets and typography through their
existing account authorities and pass those resolved values into the
generator. The generator performs no account lookup or network discovery.

For an ordinary Page, `settingsLocales` comes from current account Settings at
the explicit Save or Update operation. For a Page template it is empty and no
locale output is produced.

The generator does not receive or infer a tier. Bob/Roma's existing product
state determines the approved Instance toggle and attribution values supplied
to the browser. Pages have no SEO boolean because every ordinary Page receives
Page SEO/GEO/AEO output.

## 6. Generic HTML rendering

Move the existing pure stencil-renderer implementation into Web Code Generator
as the one generic HTML renderer. Bob imports the new owner; the Bob-local copy
is deleted.

The renderer must support:

- values;
- conditions;
- repeaters;
- nested repeaters;
- exact editable field paths;
- the existing escaped-text, approved raw-content, and parent-context
  behavior.

Repeater rendering exposes the current item index and parent path so generated
markup receives concrete paths:

```text
faq.sections.0.faqs.1.answer
```

It must never emit unresolved wildcard paths such as:

```text
faq.sections[].faqs[].answer
```

This is one improvement to the existing generic renderer. Do not add
per-Widget renderers, Widget TypeScript writers, or another template language.

If a value or repeater required by the Widget definition is missing or has the
wrong shape, generation fails visibly. The renderer must not silently turn
invalid required source into empty HTML.

## 9. Page generation

Web Code Generator runs for a Page only when the customer explicitly chooses
**Save** or **Update page**.

It does not run when the customer:

- opens Page Builder;
- changes a draft control;
- lists Pages;
- changes account Settings;
- clicks Generate translations;
- publishes;
- visits a public URL.

On Save or Update, Page Builder supplies:

- the Page source;
- current Settings locales;
- each ordered referenced saved Instance's structured source and exact saved
  `index.html`, `styles.css`, and `runtime.js`;
- current saved Page and Instance overlays;
- required account asset and typography values already available to the
  editor.

Web Code Generator returns:

- one complete Page `index.html`;
- one Page `styles.css`;
- one behavior-only Page `runtime.js`;
- for an ordinary Page, one `overlays.json` containing locale values only.

The result contains no revision snapshot, fingerprint, package version,
candidate identifier, or generated-from record.

If a required input is unavailable and generation cannot complete, Save or
Update fails with the normal retry interaction. No special failure state is
created.

## 10. Page HTML

Page `index.html` is one complete semantic document.

It contains:

- Page head and body structure;
- Page title and approved metadata;
- ordered Instance placements;
- each child Instance's meaningful HTML in the initial response;
- declarative open Shadow DOM for placement isolation;
- locale field-path markers used by public response completion;
- the localized `WebPage` JSON-LD and supported FAQ contribution defined in
  Section 15.

A Clickeen Page never:

- stacks public Widget URLs;
- uses an iframe for a child Instance;
- runs `clickeen.js` once per child Instance;
- waits for JavaScript to create primary content.

## 11. Page CSS

Page CSS must support multiple Widget types and multiple differently styled
Instances of the same Widget on one Page.

Use this rule:

1. include shared Widget structure rules once per Widget type in first-use
   order;
2. express each Instance's visual choices as CSS custom properties on that
   placement root;
3. add `<link rel="stylesheet" href="./styles.css">` inside each placement's
   declarative Shadow DOM template so every shadow root can use the shared
   stylesheet while the browser fetches the same URL once;
4. keep Page-owned layout CSS separate from Widget rules.

Example:

```html
<section
  data-ck-placement-id="HERO"
  style="--ck-heading-color:#111;--ck-card-radius:1rem"
>
  <template shadowrootmode="open">
    <link rel="stylesheet" href="./styles.css">
    <!-- complete Instance HTML -->
  </template>
</section>
```

Two placements of the same Widget type therefore share structure rules while
retaining independent values.

Do not add selector rewriting, per-placement CSS file copies, a CSS registry,
or a new module framework.

## 12. Page runtime

Page `runtime.js` contains only behavior needed by the included Instances and
the Page itself.

- include shared behavior once in first-use order;
- initialize each placement root independently;
- read required behavior settings from that placement's completed HTML;
- do not embed customer source or overlay maps in JavaScript;
- do not create headings, lists, cards, links, images, or other primary
  customer content.

Keep and reuse the existing stable style/runtime module markers where they are
already the source authority. Do not invent a second marker scheme, dependency
graph, chunk registry, or runtime loader.

## 13. `overlays.json`

Generated `overlays.json` is deliberately small. It contains only
locale-specific values needed to complete the generated Page HTML.

```ts
type PageServingOverlays = Record<
  string,
  {
    page: Record<string, string>;
    placements: Record<string, Record<string, unknown>>;
  }
>;
```

Example:

```json
{
  "it-IT": {
    "page": {
      "title": "Titolo italiano",
      "description": "Descrizione italiana"
    },
    "placements": {
      "HERO": {
        "header.title": "Benvenuti"
      }
    }
  }
}
```

The top-level key is the exact locale. `page` contains Page-owned translated
values. `placements` contains the referenced Instance overlay values keyed by
placement ID and their existing field paths. Both objects are always present;
either may be empty when that locale has no values in that scope.

`overlays.json` does not contain:

- `baseLocale`;
- the account Settings locale list;
- country or market routing;
- publication state;
- tier or policy values;
- revisions or timestamps;
- fingerprints or generation evidence.

Base-locale values are already present in `index.html`. Templates do not
produce `overlays.json`.

Account Settings locales are the allowed locale list, not proof that a saved
Page translation already exists. The first Page Save therefore succeeds with
base-locale output when no Page overlays exist. A non-base locale appears in
generated `overlays.json` and the Page's alternate-locale links only after its
saved Page overlay exists, normally after Generate translations followed by
Save or Update. A present malformed Page overlay fails generation, and a
present Page overlay outside the current Settings locale list also fails; the
generator does not publish either one.

## 14. Locale response markers

Generated HTML uses one small field-path contract so Tokyo can place exact
locale values into complete HTML before returning the response:

- `data-ck-field-path` names the exact saved field path;
- `data-ck-field-target` identifies text, approved rich text, or an approved
  `alt`, `title`, or metadata `content` attribute;
- Page placement roots use `data-ck-placement-id`;
- standalone Instance roots keep their existing Instance coordinate.

The base value is already present in the HTML. `runtime.js` does not apply
overlays or rebuild the DOM.

Reuse the existing text, rich-text, attribute, URL, and translation safety
behavior. Do not create a shared validator framework or a second response-
marker system.

## 15. Page SEO/GEO/AEO

Every ordinary Page receives SEO/GEO/AEO output because Pages start at Tier 2.

There is:

- no Page SEO toggle;
- no Page `seoGeoAeoEnabled` field;
- no Page SEO entitlement input to Web Code Generator.

Web Code Generator emits:

- the saved Page title and description;
- canonical and alternate-locale relationships;
- social title from the supplied locale-specific social-title override, or
  from that locale's Page title when no override exists;
- social description from the supplied locale-specific social-description
  override, or from that locale's Page description when no override exists;
- the supplied social image when one exists;
- `index,follow` or `noindex,follow` from the saved Page search-visibility
  choice;
- one localized `WebPage` JSON-LD block;
- content-specific structured data only when a supported Widget declares it
  from visible source content;
- locale field markers so translated metadata appears in the complete
  locale-specific HTML response.

The `WebPage` JSON-LD block is part of Page `index.html` and has this exact
contract:

| Property | Value |
| --- | --- |
| `@context` | `https://schema.org` |
| `@type` | `WebPage` |
| `@id` | Exact-locale public Page URL followed by `#webpage` |
| `url` | Exact-locale public Page URL |
| `name` | Effective localized Page title |
| `description` | Effective localized Page description, omitted when empty |
| `inLanguage` | Exact requested locale |
| `primaryImageOfPage` | `{ "@type": "ImageObject", "contentUrl": <supplied social image URL> }`, omitted when no image exists |

Web Code Generator writes the base-locale block and the same field-path,
schema, and public-coordinate markers used by the rest of the Page head.
127C makes Tokyo apply the saved exact-locale values and public URL before it
returns and caches exact-locale HTML. 127B does not duplicate that serving
work. No browser JavaScript builds or changes the block.

Of the current Widgets, only FAQ may contribute content-specific schema. When
present, its `FAQPage` data comes only from questions and answers that are also
visible in the Page HTML. Other Widget types do not receive inferred content
schema. This rule adds no schema registry, schema service, agent operation, or
customer-facing structured-data form.

The fallback values are resolved while writing public HTML. They are not copied
back into Page source or overlays. If neither a social-description override nor
a Page description exists, omit the social-description tag. Web Code Generator
does not infer Page title or description from the internal Page name or from
arbitrary Widget content.

It does not invent keywords, locations, claims, descriptions, schema values,
or search outcomes.
