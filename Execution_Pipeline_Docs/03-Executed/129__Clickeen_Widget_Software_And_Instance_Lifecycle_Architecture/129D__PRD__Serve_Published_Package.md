## 1. Outcome

129D defines one product action:

```text
public request
-> read stored publication truth
-> return the stored published HTML, CSS, and JavaScript
```

Serve does not create, edit, Save, Publish, materialize, translate, or rebuild
an instance.

## 2. Input From 129C

Serve receives only stored account-instance truth:

```text
published instance identity
+
serve-state.json containing:
  status: published
  publishedAt
  publicPackage:
    indexHtml
    stylesCss
    runtimeJs
+
zero or more exact locale overlays
```

The three logical public file members were generated by Roma's materializer
during the last successful Publish. Tokyo-worker stored them atomically with
publication truth in that one artifact. There are no separate `index.html`,
`styles.css`, or `runtime.js` storage objects. The existing public URLs retain
those filenames and select the corresponding exact logical member.

## 3. Starting Implementation Mismatch

Tokyo-worker already owned public account-instance serving, but before this
local PRD 129 pass public HTML carried locale context for browser JavaScript to
apply and runtime JavaScript performed work that belongs to materialization or
the Edge response.

129D corrects that boundary:

- Publish generates complete base HTML/CSS/JavaScript;
- Tokyo-worker expresses an exact selected locale in returned HTML; and
- browser JavaScript handles visitor functionality, not initial content or
  localization.

## 4. Base-Locale Request

For a base-locale public request, Tokyo-worker returns the stored package:

- the public `index.html` response uses exact `publicPackage.indexHtml` and
  contains complete meaningful base-locale content;
- the public `styles.css` response uses exact `publicPackage.stylesCss` and
  contains complete presentation; and
- the public `runtime.js` response uses exact `publicPackage.runtimeJs` and
  contains the Widget's visitor-facing functionality.

Tokyo-worker does not invoke Roma or the materializer and does not regenerate
the package.

## 5. Selected-Locale Request

For an available non-base locale, Tokyo-worker reads the exact stored locale
overlay and expresses every present stable-coordinate value in the returned
HTML before client JavaScript. A newly added identity intentionally retains its
saved base text until the user explicitly runs Generate Translations. A
deleted identity has no current node on which an old overlay coordinate can
act.

The response contains selected-locale headings, questions, answers, links, and
technical Discovery content for the exact coordinates present in the stored
overlay. Intentional untranslated source content remains meaningful HTML; it
is not a fallback to another locale or an invented translation.

`styles.css` and `runtime.js` remain exact logical members of the stored base
package. There is no locale-specific package copy and no browser localization
step.

Missing selected-locale truth does not fall back to another locale.

The generic mapping is implemented with authored `data-ck-content-path` and
`data-ck-content-mode` attributes on materialized customer-content elements.
The path is the stable identity coordinate, not a positional array path. For
an editable attribute, the authored slot also names the exact target with
`data-ck-content-attribute`. Tokyo-worker's Cloudflare `HTMLRewriter` applies
each present trusted value to that exact attribute or, when no attribute target
is authored, to the element body. It then sets `<html lang>` to the requested
locale. FAQ Core's enabled Discovery microdata wraps those same visible
question/answer slots, so localized content and its relationship stay together
without a second Discovery rewrite.

## 6. Unpublished Instance

An unpublished instance is not publicly served.

Its editable source remains available through the authenticated account and
Bob flows. Public serving neither deletes nor changes that source.

## 6.1 Account Lifecycle Handoff

Serve does not know the account tier or account-suspension clock and does not
enforce either policy on a visitor request. It consumes only the publication
truth already produced by the owning account operation.

The settled account-suspension lifecycle is a 30-day public-serving grace
period, automatic free-tier serving materialization at day 30 if the account
has not recovered, and automatic account-root deletion at day 90 if recovery
still has not occurred. The scheduled lifecycle runner and complete account-
root deletion operation remain documented account-lifecycle implementation
gaps. They are outside PRD 129 and do not block this Serve boundary.

There is no per-view tier lookup, lifecycle calculation, package rewrite,
automatic fallback, or Widget-specific account-policy branch in public
serving.

Locale overlays now use stable coordinates derived from saved
`arrayItemIdentity` values. Reorder follows identity, newly added identities
remain explicitly untranslated until Generate Translations, and deleted
identities have no current node. This is a pre-GA coordinate cutover for scalar
and repeated fields: old positional overlays require explicit Generate
Translations or explicit deletion after deployment. Serve has no compatibility
read, migration-on-request, validator, guess, or fallback.

## 7. Serving Law

Tokyo-worker serves exact stored truth under the existing public account and
instance route.

A visitor request never:

- calls Bob;
- calls Roma;
- invokes the materializer;
- reads Widget authoring source;
- calls a model or agent;
- regenerates translations;
- rebuilds HTML, CSS, or JavaScript;
- changes publication state;
- decides or reconciles account lifecycle;
- consumes another publication slot; or
- repairs missing or corrupt state.

Serving work is intentionally small because the expensive product work
happened once at Publish.

Successful base and selected-locale package responses use
`public, max-age=60, s-maxage=300, must-revalidate`. The locale query is part of
the request cache coordinate. Missing or unreadable locale truth uses explicit
non-cacheable error responses. After Publish, Unpublish, overlay mutation, or
Delete commits, Tokyo's default Worker entrypoint schedules its exact
account-instance Cache-Tag eviction through `waitUntil`. Eviction never affects
the owning mutation's response. No service or user observes a purge result,
maintains cache failure state, or performs cache retry/reconciliation. Serve
does not probe or rebuild state.

For Delete, the exact `instance.source.json` removal is the logical commit.
Tokyo's serving path reads that source anchor before `serve-state.json`, so an
uncached request cannot reach residual publication or overlay objects after
the anchor is gone. The default entrypoint schedules residual prefix cleanup
through `waitUntil`; cleanup success, rejection, or failure is as product-inert
as cache eviction.

## 8. Why This Wins

### Edge serving

Tokyo-worker returns stored logical browser-file members instead of rebuilding
a Widget for each visitor. One Publish can therefore serve many requests
cheaply and quickly.

### Search, GEO, and AEO

Search crawlers, generative systems, and answer engines receive real saved
content and relationships in HTML without executing an initial client
renderer.

### Localization

The selected-locale response contains localized meaningful HTML before
JavaScript without storing a second package per locale.

### Browser behavior

The browser still receives mandatory JavaScript for actual Widget
functionality. HTML, CSS, and JavaScript each keep their normal browser role.

This architecture improves access to content; it does not guarantee search
ranking, citations, or answer-engine selection.

## 11. Implemented Serving Boundary

- publication truth and the exact logical public package are one
  `serve-state.json` through the existing source pointer read;
- base `index.html`, `styles.css`, and `runtime.js` public responses select
  exact `indexHtml`, `stylesCss`, and `runtimeJs` members from that artifact;
- no separate package storage objects or compatibility reads exist;
- selected-locale HTML uses generic content-slot attributes and Cloudflare
  `HTMLRewriter`, including an authored exact attribute target where required;
- present overlay values are keyed by stable scalar/repeated identity
  coordinates; a missing new-identity value leaves its exact saved base text
  unchanged, and a deleted identity has no current node;
- missing locale truth returns `404 Locale not available`;
- an unreadable overlay returns `500 Locale data invalid`;
- unpublished truth returns `404`; a published artifact is trusted to contain
  its exact logical package and never falls back to prior package objects;
- a missing `instance.source.json` returns `404` before publication or overlay
  reads; post-Delete residual prefix objects remain unreachable until their
  product-inert background cleanup completes;
- base and selected-locale success responses retain the existing public cache
  policy; and
- no request reads account tier or performs account-lifecycle reconciliation.

This required a pre-GA storage cutover. The corrected runtime discovers an
instance only through its exact `instance.source.json`, so each legacy saved
cloud-dev instance using the former config/content split required an explicit
source cutover or recreation decision. Each instance intended to remain
published then required an explicit Publish/Republish so its `serve-state.json`
received the logical `publicPackage`. Serve has no legacy source reader and no
separate-package-object fallback. The completed cloud-dev cutover and
publication actions are recorded in §14.

The scheduled suspension-lifecycle runner and full account-root deletion
operation were not added. Serve consumes only the publication truth that
exists; those account-lifecycle gaps remain outside PRD 129.

For an index response, Tokyo-worker lists the exact stored overlay coordinates
and authors the base locale plus those coordinates as the switcher's `<option>`
elements. The shared runtime reads those authored options; it does not need a
public locale-policy global and does not invent options from `<html lang>`.
Missing public options fail visibly. Bob preview alone builds temporary options
from its exact `CK_LOCALE_POLICY` editing input; a missing preview policy also
fails visibly, and option text is the delivered locale coordinate rather than
a fallback label source.

## 15. Closure Serving Correction

The live closure audit proved that Tokyo's generic overlay lookup is correct
and the stored FAQ overlays already carry exact current stable identity keys.
The prior deployed FAQ package was wrong: its repeated
`data-ck-content-path` attribute values contained Mustache's escaped
`&#x3D;` text instead of the canonical literal `=`. Consequently a
selected-locale request could replace scalar slots while leaving repeated
questions and answers in base English.

The serving correction was intentionally no Tokyo fix. The materializer
producer now emits the canonical literal coordinate; Tokyo continues comparing
the exact trusted attribute value with the exact trusted overlay key. After
deployment and explicit Republish of `VUWUJ7OQ0Y`, unique French public HTML
proved both repeated FAQ question and answer values changed through the stored
overlay, scalar localization remained correct, base serving remained complete,
and no Widget-specific branch, decoder, fallback, or runtime repair exists.
The SubPRD is executed and closed by agent-executed functionality proof.
